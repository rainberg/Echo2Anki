## 1. 项目背景与目标

### 1.1 背景

当前 Anki 音频处理系统（V2 版）是一个基于 Streamlit 的单用户应用，运行在 Oracle Cloud ARM 实例上。系统实现了从德语音频上传到 Anki 卡片推送的完整流水线，包括音频标准化、语音识别（Whisper）、句子对齐切分、德译中翻译、逐句播放、收藏管理和 Anki 同步推送。

该系统目前仅面向单一用户使用，无认证、无计费、无分类，数据以 JSON 文件存储在文件系统中。

### 1.2 重构目标

将现有单用户系统重构为面向普通用户的多用户 SaaS 平台，核心目标：

| 目标 | 说明 |
|------|------|
| **多用户支持** | 用户注册/登录，数据隔离，权限控制 |
| **计费系统** | 按音频时长计费（分钟为单位），引擎差异化定价 |
| **分类与复用** | 标签系统、收藏集、全局搜索、公共库 |
| **前端现代化** | Vue 3 替代 Streamlit，为跨平台做准备 |
| **平滑过渡** | 新旧版本并行运行，渐进式迁移 |

### 1.3 约束条件

- 服务器资源有限（4 核 ARM / 24GB RAM / 无 GPU）
- 保留现有 Streamlit 版本在过渡期可用
- 不迁移历史数据，旧数据仅作验证用途
- 初期充值方式为管理员手动操作

## 2. 现有系统分析

### 2.1 技术栈

| 组件 | 技术 |
|------|------|
| 前端 | Streamlit (Python) |
| 后端 | Streamlit + Python threading |
| 存储 | JSON 文件（status.json + manifest.json） |
| Web 服务器 | Nginx 反向代理 → Streamlit :8501 |
| 进程管理 | systemd |
| 音频处理 | faster-whisper + pydub + deep-translator |
| Anki 推送 | 自建 Anki 同步服务器 (sync_client) + AnkiWeb (官方同步协议) |

### 2.2 核心文件清单

| 文件 | 职责 | 代码行数 |
|------|------|----------|
| `app_v2.py` | Streamlit 前端主页面 | ~820 行 |
| `task_worker.py` | 后台任务引擎（队列、流水线、取消） | ~700 行 |
| `align_and_cut.py` | 音频对齐切分 | ~500 行 |
| `anki_push_router.py` | Anki 推送路由 | ~26 行 |
| `anki_sync_client_push.py` | Anki 自建服务器推送（sync_client 模式） | ~300 行 |
| `ankiweb_push.py` | AnkiWeb 官方同步推送 | ~200 行 |
| `normalize_audio.py` | 音频标准化脚本 | ~50 行 |
| `whisper_timestamps.py` | Whisper 时间戳提取 | ~90 行 |
| `subtitle_component/` | HTML5 自定义播放器组件 | HTML/JS |

### 2.3 数据模型（现有）

```
任务目录: /var/lib/anki-v2/tasks/{task_id}/
├── status.json        ← 任务状态（stage, progress, error）
├── manifest.json      ← 处理结果（segments, translations, favorites）
├── source.mp3         ← 原始音频
├── source.normalized.mp3  ← 标准化音频
├── clips/             ← 逐句切分音频
│   ├── clip_001.mp3
│   ├── clip_002.mp3
│   └── ...
└── cancel.json        ← 取消标记（存在即表示已取消）
```

### 2.4 现有系统问题

| 问题 | 现状 | 影响 |
|------|------|------|
| 单用户 | 无认证，所有人共享 | 无法区分用户，无法计费 |
| JSON 文件存储 | 散落在文件系统 | 无法高效查询、统计、关联 |
| 无计费 | 完全免费 | 无法商业化 |
| 无分类 | 任务仅按时间排序 | 积累后难以查找复用 |
| Streamlit 局限 | session_state 不持久 | 多用户场景力不从心 |
| 单 worker | 同时仅处理 1 个任务 | 吞吐量受限 |

## 3. 需求确认

### 3.1 功能需求

| 编号 | 需求 | 优先级 | 说明 |
|------|------|--------|------|
| F-01 | 用户注册/登录 | P0 | 邮箱+密码，JWT 认证 |
| F-02 | 多用户数据隔离 | P0 | 用户只能访问自己的任务和收藏 |
| F-03 | 按时长计费 | P0 | 以分钟为单位，任务提交时预扣 |
| F-04 | 引擎差异化定价 | P0 | 不同引擎不同单价，管理员配置 |
| F-05 | 管理员指定用户可用引擎 | P0 | 按用户控制可用引擎列表 |
| F-06 | 管理员手动充值 | P0 | 管理员后台为用户充值分钟数 |
| F-07 | 标签分类 | P1 | 用户自定义标签，任务打标签 |
| F-08 | 收藏集 | P1 | 命名收藏组，替代单一收藏列表 |
| F-09 | 全局搜索 | P1 | 跨任务搜索德语/中文句子 |
| F-10 | 公共库 | P1 | 用户可公开任务，他人可浏览收藏 |
| F-11 | 音频库视图 | P1 | 按标签/日期/时长筛选已完成任务 |
| F-12 | Vue 3 前端 | P0 | 替代 Streamlit，为跨平台准备 |
| F-13 | 旧版并行 | P0 | Streamlit 旧版在 /legacy/ 可用 |
| F-14 | Anki 推送 | P1 | 从收藏集推送卡片到 Anki，支持自建 Anki 服务器和 AnkiWeb 两种方式 |

### 3.2 非功能需求

| 编号 | 需求 | 目标 |
|------|------|------|
| NF-01 | 并发用户 | 支持 10+ 并发浏览用户 |
| NF-02 | 任务吞吐 | 支持 2 个任务同时处理 |
| NF-03 | 响应时间 | API 响应 < 500ms（非转写操作） |
| NF-04 | 数据安全 | 用户数据隔离，密码 bcrypt 加密 |
| NF-05 | 可扩展性 | 架构支持水平扩展 |
| NF-06 | 可维护性 | 前后端分离，API 文档自动生成 |

### 4.2 请求流程

**上传音频处理流程**：

```
用户 → Vue 前端 → POST /api/tasks (multipart)
                         │
                    FastAPI 验证
                    ├── JWT 认证
                    ├── 检查用户可用引擎
                    ├── 估算时长 → 预扣 credits
                    ├── 写入 DB (tasks 表, stage=pending)
                    ├── 保存文件到 /var/lib/anki/tasks/{uid}/{task_id}/
                    ├── 入队 TaskWorker
                    └── 返回 task_id
                         
                    TaskWorker 消费
                    ├── 标准化 → 更新 DB (stage=normalizing)
                    ├── 获取精确时长 → 结算 credits
                    ├── 转写 → 更新 DB (stage=transcribing)
                    ├── 翻译 → 更新 DB (stage=translating)
                    ├── 写入 segments 表
                    └── 更新 DB (stage=done)

用户 → Vue 前端 → GET /api/tasks/{id} (轮询进度)
                    └── FastAPI → 查询 DB → 返回进度
```

**播放与收藏流程**：

```
用户 → Vue 前端 → GET /api/tasks/{id}/segments
                    └── FastAPI → 查询 DB → 返回句子列表

用户 → Vue 前端 → POST /api/collections/{id}/add
                    └── FastAPI → 写入 collection_items 表

用户 → Vue 前端 → POST /api/push
                    └── FastAPI → 调用 anki_push_router → 推送到 Anki 服务器
```

### 4.3 进度推送方案

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| HTTP 轮询 | 实现简单，兼容性好 | 延迟高，请求多 | ✅ Phase 1 |
| WebSocket | 实时推送，体验好 | 实现复杂 | ✅ Phase 2+ |
| SSE | 单向实时，比 WS 简单 | 浏览器兼容性 | 备选 |

初期采用前端 3 秒轮询 `GET /api/tasks/{id}`，后续升级为 WebSocket 实时推送。

### 5.2 完整 DDL

```sql
-- ============================================================
-- 用户与权限
-- ============================================================

CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           VARCHAR(255) UNIQUE NOT NULL,
    password_hash   VARCHAR(255) NOT NULL,
    display_name    VARCHAR(100),
    role            VARCHAR(20) DEFAULT 'user' CHECK (role IN ('user', 'admin')),
    credits         DECIMAL(10,2) DEFAULT 0 CHECK (credits >= 0),
    allowed_engines TEXT[] DEFAULT '{local_whisper}',
    is_active       BOOLEAN DEFAULT TRUE,
    created_at      TIMESTAMPTZ DEFAULT NOW(),
    updated_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_users_role ON users(role);

-- ============================================================
-- 引擎定价（管理员配置）
-- ============================================================

CREATE TABLE engine_pricing (
    engine_key         VARCHAR(30) PRIMARY KEY,
    engine_name        VARCHAR(100) NOT NULL,
    credits_per_minute DECIMAL(10,4) NOT NULL CHECK (credits_per_minute > 0),
    is_active          BOOLEAN DEFAULT TRUE,
    sort_order         INTEGER DEFAULT 0,
    description        TEXT DEFAULT ''
);

INSERT INTO engine_pricing (engine_key, engine_name, credits_per_minute, is_active, sort_order, description) VALUES
    ('local_whisper',    '本地 Whisper (faster-whisper)', 1.0,  TRUE, 1, '使用服务器本地 faster-whisper 模型，支持 tiny/base/small/medium'),
    ('openai_whisper',   'OpenAI Whisper API',            2.0,  TRUE, 2, '使用 OpenAI Whisper 云端 API，需要 API Key'),
    ('cohere',           'Cohere ASR',                    1.5,  TRUE, 3, '使用 Cohere 语音识别服务');

-- ============================================================
-- 任务
-- ============================================================

CREATE TABLE tasks (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id           UUID NOT NULL REFERENCES users(id),
    upload_name       VARCHAR(500) NOT NULL,
    file_hash         VARCHAR(64) NOT NULL,
    file_duration_sec DECIMAL(10,2),
    file_size_bytes   BIGINT,
    engine            VARCHAR(30) NOT NULL DEFAULT 'local_whisper',
    model_size        VARCHAR(20) DEFAULT 'small',
    stage             VARCHAR(20) DEFAULT 'pending'
                      CHECK (stage IN ('pending','normalizing','transcribing','translating','done','failed','cancelled')),
    progress          DECIMAL(5,4) DEFAULT 0 CHECK (progress >= 0 AND progress <= 1),
    stage_message     TEXT DEFAULT '',
    error             TEXT DEFAULT '',
    source_path       VARCHAR(500),
    normalized_path   VARCHAR(500),
    clips_dir         VARCHAR(500),
    segment_count     INTEGER DEFAULT 0,
    credits_charged   DECIMAL(10,2) DEFAULT 0,
    credits_reserved  DECIMAL(10,2) DEFAULT 0,
    is_public         BOOLEAN DEFAULT FALSE,
    created_at        TIMESTAMPTZ DEFAULT NOW(),
    started_at        TIMESTAMPTZ,
    finished_at       TIMESTAMPTZ,

    UNIQUE(user_id, file_hash)
);

CREATE INDEX idx_tasks_user_id ON tasks(user_id);
CREATE INDEX idx_tasks_stage ON tasks(stage);
CREATE INDEX idx_tasks_created_at ON tasks(created_at DESC);
CREATE INDEX idx_tasks_is_public ON tasks(is_public) WHERE is_public = TRUE;
CREATE INDEX idx_tasks_engine ON tasks(engine);

-- ============================================================
-- 句子
-- ============================================================

CREATE TABLE segments (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id       UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    seq_index     INTEGER NOT NULL CHECK (seq_index > 0),
    start_time    DECIMAL(8,3) NOT NULL,
    end_time      DECIMAL(8,3) NOT NULL,
    german_text   TEXT NOT NULL,
    chinese_text  TEXT DEFAULT '',
    clip_path     VARCHAR(500),

    UNIQUE(task_id, seq_index)
);

CREATE INDEX idx_segments_task_id ON segments(task_id);

-- 全文搜索索引（德语 + 中文）
CREATE INDEX idx_segments_german_trgm ON segments USING gin (german_text gin_trgm_ops);
CREATE INDEX idx_segments_chinese_trgm ON segments USING gin (chinese_text gin_trgm_ops);

-- ============================================================
-- 收藏集
-- ============================================================

CREATE TABLE collections (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID NOT NULL REFERENCES users(id),
    name          VARCHAR(200) NOT NULL,
    description   TEXT DEFAULT '',
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    updated_at    TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_collections_user_id ON collections(user_id);

-- ============================================================
-- 收藏项（句子 → 收藏集）
-- ============================================================

CREATE TABLE collection_items (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    collection_id   UUID NOT NULL REFERENCES collections(id) ON DELETE CASCADE,
    segment_id      UUID NOT NULL REFERENCES segments(id),
    push_enabled    BOOLEAN DEFAULT TRUE,
    added_at        TIMESTAMPTZ DEFAULT NOW(),

    UNIQUE(collection_id, segment_id)
);

CREATE INDEX idx_collection_items_collection ON collection_items(collection_id);
CREATE INDEX idx_collection_items_segment ON collection_items(segment_id);

-- ============================================================
-- 标签
-- ============================================================

CREATE TABLE tags (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id       UUID NOT NULL REFERENCES users(id),
    name          VARCHAR(100) NOT NULL,
    color         VARCHAR(7) DEFAULT '#4A90D9',
    created_at    TIMESTAMPTZ DEFAULT NOW(),

    UNIQUE(user_id, name)
);

CREATE INDEX idx_tags_user_id ON tags(user_id);

-- ============================================================
-- 任务-标签关联
-- ============================================================

CREATE TABLE task_tags (
    task_id       UUID NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    tag_id        UUID NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
    PRIMARY KEY (task_id, tag_id)
);

-- ============================================================
-- 计费记录
-- ============================================================

CREATE TABLE billing_records (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id           UUID NOT NULL REFERENCES users(id),
    task_id           UUID REFERENCES tasks(id),
    action            VARCHAR(30) NOT NULL CHECK (action IN ('charge','topup','refund','reserve','settle')),
    amount            DECIMAL(10,2) NOT NULL,
    balance_after     DECIMAL(10,2) NOT NULL,
    duration_sec      DECIMAL(10,2),
    description       TEXT,
    created_at        TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_billing_user_id ON billing_records(user_id);
CREATE INDEX idx_billing_task_id ON billing_records(task_id);
CREATE INDEX idx_billing_created_at ON billing_records(created_at DESC);

-- ============================================================
-- Anki 推送配置
-- ============================================================

CREATE TABLE anki_push_configs (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
```

```sql
       t.engine, t.created_at, u.display_name,
       array_agg(tg.name) AS tag_names
FROM tasks t
JOIN users u ON t.user_id = u.id
LEFT JOIN task_tags tt ON t.id = tt.task_id
LEFT JOIN tags tg ON tt.tag_id = tg.id
WHERE t.is_public = TRUE AND t.stage = 'done'
GROUP BY t.id, u.display_name
ORDER BY t.created_at DESC
LIMIT 20;

-- 全局搜索句子

       t.id AS task_id, t.upload_name, t.user_id
FROM segments s
JOIN tasks t ON s.task_id = t.id
WHERE (s.german_text ILIKE '%' || :q || '%'
    OR s.chinese_text ILIKE '%' || :q || '%')
  AND (t.user_id = :uid OR t.is_public = TRUE)
ORDER BY s.german_text <-> :q LIMIT 50;

-- 用户余额与用量统计
SELECT u.credits,
       COUNT(t.id) AS total_tasks,
       SUM(CASE WHEN t.stage = 'done' THEN 1 ELSE 0 END) AS done_tasks,
       COALESCE(SUM(t.file_duration_sec), 0) AS total_duration_sec,
       COALESCE(SUM(t.credits_charged), 0) AS total_credits_used
FROM users u
LEFT JOIN tasks t ON u.id = t.user_id
```

## 7. 计费系统设计

### 7.1 计费模型

```
计费单位: 分钟 (1 credit = 1 分钟音频时长)
计费依据: 音频文件的实际时长 (file_duration_sec)
定价方式: 按引擎差异化定价 (engine_pricing 表)
```

### 7.2 引擎定价

| 引擎 | 默认单价 (credits/分钟) | 说明 |
|------|------------------------|------|
| local_whisper | 1.0 | 服务器本地 faster-whisper，CPU 推理 |
| openai_whisper | 2.0 | OpenAI Whisper API，需 API Key |
| cohere | 1.5 | Cohere ASR 服务 |

管理员可通过 `/api/admin/engine-pricing/` 动态调整价格。

### 7.3 计费流程

```
                        用户提交任务
                             │
                    ┌────────▼────────┐
                    │ 1. 估算最大时长   │
                    │    max_duration  │
                    │    = file_size   │
                    │    / min_bitrate │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │ 2. 预扣 credits  │
                    │    reserve =     │
                    │    max_duration  │
                    │    × price/min   │
                    │    × 1.2 (缓冲)  │
                    └────────┬────────┘
                             │
                 ┌───────────┼───────────┐
                 │           │           │
          ┌──────▼──────┐ ┌──▼───────┐ ┌▼──────────┐
          │ 3a. 标准化   │ │ 3b. 取消  │ │ 3c. 失败   │
          │ 获取精确时长  │ │ 退还预扣  │ │ 退还预扣   │
          │ 结算实际费用  │ │           │ │            │
          │ 退还差额     │ │           │ │            │
          └──────┬──────┘ └──────────┘ └────────────┘
                 │
          ┌──────▼──────┐
          │ 4. 处理完成   │
          │ 记录最终费用  │
          └─────────────┘
```

### 7.4 计费操作类型

| action | 说明 | amount |
|--------|------|--------|
| `reserve` | 预扣 | 负数 |
| `settle` | 结算（标准化后精确计费） | 正数（退还差额）或负数（补扣） |
| `charge` | 最终扣费 | 负数 |
| `refund` | 退还（取消/失败） | 正数 |
| `topup` | 充值 | 正数 |

### 7.5 并发安全

使用 PostgreSQL 行级锁确保 credits 操作原子性：

```python
async def reserve_credits(db: AsyncSession, user_id: UUID, amount: Decimal) -> bool:
    stmt = select(User).where(User.id == user_id).with_for_update()
    result = await db.execute(stmt)
    user = result.scalar_one_or_none()
    if not user or user.credits < amount:
        return False
    user.credits -= amount
    await db.flush()
    return True
```

## 10. Anki 推送系统设计

### 10.1 现有推送实现分析

当前系统包含三种 Anki 推送实现：

| 实现 | 文件 | 原理 | 优缺点 |
|------|------|------|--------|
| **sync_client** | `anki_sync_client_push.py` | 本地 collection 缓存 + Anki 同步协议 → 自建服务器 | ✅ 安全（不直写 DB）✅ 支持媒体同步 ❌ 需要自建服务器 ❌ 需要文件锁 |
| **ankiweb** | `ankiweb_push.py` | 本地 collection 缓存 + Anki 官方同步协议 → AnkiWeb | ✅ 无需自建服务器 ✅ 用户自带账号 ❌ 需要 AnkiWeb 账号 ❌ 受 AnkiWeb 速率限制 |

### 10.2 新系统推送架构

重构后统一为两种推送模式，用户在推送时选择：

```
┌─────────────────────────────────────────────────────┐
│                  用户选择推送方式                      │
│                                                      │
│   ┌──────────────────┐    ┌──────────────────────┐  │
│   │ 自建 Anki 服务器   │    │  AnkiWeb 官方同步     │  │
│   │ (Self-hosted)    │    │  (ankiweb.net)       │  │
│   └────────┬─────────┘    └──────────┬───────────┘  │
│            │                         │               │
│   ┌────────▼─────────┐    ┌──────────▼───────────┐  │
│   │ sync_client 模式  │    │ AnkiWeb 官方协议      │  │
│   │                  │    │                      │  │
│   │ 本地缓存 → 同步   │    │ 本地缓存 → 同步      │  │
│   │ → 自建服务器      │    │ → ankiweb.net        │  │
│   └──────────────────┘    └──────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

**统一推送接口**：

```python
class AnkiPusher(Protocol):
    async def push(
        self,
        sentences: List[Dict],
        audio_dir: str,
        deck_name: str,
    ) -> PushResult: ...

class PushResult(TypedDict):
    success: bool
    count: int
    skipped: int
    deck_name: str
    message: str
    push_mode: str
```

### 10.3 自建 Anki 服务器推送

**适用场景**：用户使用平台托管的 Anki 同步服务器

**实现方式**：复用现有 `anki_sync_client_push.py` 的 sync_client 模式

```
推送流程:
  1. 获取文件锁（防止并发推送冲突）
  2. 打开本地 collection 缓存
  3. 与自建服务器同步（下载最新数据）
  4. 添加笔记和卡片到指定牌组
  5. 上传同步（推送变更到服务器）
  6. 等待媒体同步完成
  7. 释放文件锁

关键配置:
  - ANKI_SYNC_ENDPOINT: 自建服务器地址 (http://127.0.0.1:8080)
  - ANKI_SYNC_USERNAME / ANKI_SYNC_PASSWORD: 同步凭证
  - ANKI_SYNC_CLIENT_CACHE_DIR: 本地缓存目录
  - ANKI_SYNC_MEDIA_TIMEOUT_SECS: 媒体同步超时

多用户适配:
  - 每个用户独立的本地 collection 缓存目录
  - 每个用户独立的文件锁
  - 共享同一自建服务器，但使用不同凭证（未来可扩展）
```

### 10.4 AnkiWeb 官方同步推送

**适用场景**：用户使用 AnkiWeb 官方同步服务，无需自建服务器

**实现方式**：复用现有 `ankiweb_push.py` 的 AnkiWeb 官方协议

```
推送流程:
  1. 用户输入 AnkiWeb 账号密码
  2. 打开本地 collection 缓存
  3. 与 AnkiWeb 同步（下载最新数据）
  4. 添加笔记和卡片到指定牌组
  5. 上传同步（推送变更到 AnkiWeb）
  6. 等待媒体同步完成

关键配置:
  - ANKIWEB_USERNAME / ANKIWEB_PASSWORD: 用户 AnkiWeb 凭证
  - ANKIWEB_CACHE_DIR: 本地缓存目录
  - ANKIWEB_NOTE_TYPE: 笔记类型名称

多用户适配:
  - 每个用户独立的本地 collection 缓存目录
  - 每个用户独立的 AnkiWeb 凭证（存储在用户配置中）
  - 凭证加密存储，不记录日志

安全注意事项:
  - AnkiWeb 凭证使用 AES-256 加密存储在数据库
  - 加密密钥由服务器主密钥派生
  - 凭证仅用于推送时解密使用，不返回给前端
  - 推送失败不重试凭证（避免锁定）
```

## 13. 服务器容量评估

### 13.1 当前硬件

| 资源 | 配置 | 当前使用率 |
|------|------|-----------|
| CPU | 4 核 ARM Neoverse-N1 (aarch64) | <1% |
| 内存 | 24 GB | 4% (908 MB) |
| 磁盘 | 146 GB (47 GB 可用) | 68% |
| GPU | 无 | — |
| 平台 | Oracle Cloud Ampere A1 (ARM) | Always Free |

### 13.2 资源消耗估算

**新增组件资源消耗**：

| 组件 | CPU | 内存 | 磁盘 |
|------|-----|------|------|
| PostgreSQL 15 | 低 | 512 MB - 2 GB | 1-5 GB |
| FastAPI (2 workers) | 低 | 200-500 MB | <100 MB |
| Vue 前端 (Nginx 静态) | 极低 | 极低 | <50 MB |
| **新增合计** | — | ~1-2.5 GB | ~2-6 GB |

**现有组件资源消耗**：

| 组件 | CPU | 内存 |
|------|-----|------|
| Streamlit V2 | 低 | ~50 MB |
| Anki Sync Server | 极低 | ~180 MB |
| Whisper small 模型 | 转写时高 | ~500 MB (加载时) |
| Whisper medium 模型 | 转写时高 | ~1.5 GB (加载时) |

### 13.3 并发容量

**瓶颈：Whisper 转写是唯一 CPU 密集操作**

| 场景 | 1 worker | 2 workers | 说明 |
|------|----------|-----------|------|
| 浏览/播放/收藏 | 50+ 并发 | 50+ 并发 | I/O 密集，几乎无上限 |
| 上传提交 | 20+ 并发 | 20+ 并发 | 仅文件上传+入队 |
| 后台转写 | 1 个同时 | 2 个同时 | CPU 是瓶颈 |
| 吞吐量 (5min 音频) | ~4-6 任务/小时 | ~8-12 任务/小时 | small 模型 CPU int8 |

**结论**：

| 用户规模 | 可行性 | 措施 |
|----------|--------|------|
| 1-10 用户 | ✅ 完全可行 | 当前配置 + 2 workers |
| 10-30 用户 | ⚠️ 需排队 | 队列机制已有，等待时间变长 |
| 30-100 用户 | ❌ 不够 | 需 GPU 实例或分离转写服务 |
| 100+ 用户 | ❌ 需重构 | K8s + GPU 集群 + 对象存储 |

### 13.4 扩容路径

```
当前 (4核 ARM / 24GB)
    ↓ 用户增长到 10+
增加 TaskWorker 到 2 并发 (仅需配置变更)
    ↓ 用户增长到 30+
增加 GPU 实例 (Oracle Cloud A1 带 GPU)
  或 分离转写为独立微服务
    ↓ 用户增长到 100+
对象存储 (S3/MinIO) 替代本地文件系统
Redis 缓存层
API 服务器水平扩展
```

## 14. 数据迁移策略

- **不迁移**历史数据到新系统
- 旧数据（字幕 Beta 版 + V2 版）作为**验证数据**使用

### 14.2 验证方案

```
1. 在新系统中手动创建测试用户
2. 使用旧数据中的音频文件重新提交任务
3. 对比新旧系统的处理结果：
   - 句子切分是否一致
   - 翻译质量是否一致
   - 音频播放是否正常
   - 收藏/推送功能是否正常
4. 验证计费逻辑：
   - 预扣 → 结算 → 退还 流程
   - 不同引擎定价是否正确
```

## 17. 风险评估与应对

### 17.1 技术风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| ARM 架构兼容性问题 | 低 | 中 | 所有依赖均已有 ARM 版本；提前测试 |
| PostgreSQL 性能不足 | 低 | 中 | 24GB 内存充裕；pg_trgm 索引优化查询 |
| Whisper CPU 转写慢 | 高 | 高 | 2 workers 提升吞吐；长期引入 GPU |
| 并发 credits 扣费竞态 | 中 | 高 | PostgreSQL 行级锁 + 事务保证原子性 |
| Vue 前端音频播放兼容性 | 中 | 中 | Howler.js 成熟方案；降级为直接链接 |
| 大文件上传超时 | 中 | 中 | Nginx client_max_body_size 500m + 分片上传 |

### 17.2 业务风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 用户增长超出服务器容量 | 中 | 高 | 队列机制限流；扩容路径已规划 |
| 计费争议 | 低 | 中 | 详细计费记录；失败全额退还 |
| 数据安全 | 中 | 高 | JWT 认证；数据隔离；密码 bcrypt；HTTPS |
| 旧版用户过渡 | 低 | 低 | /legacy/ 保留；渐进迁移 |

### 17.3 项目风险

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 开发周期超预期 | 中 | 中 | 分阶段交付；每阶段独立可用 |
| 前后端联调问题 | 中 | 中 | API 文档自动生成；Mock 数据 |
| 跨平台兼容性 | 低 | 低 | Phase 5 才涉及；Capacitor 成熟方案 |

### 18.4 术语表

| 术语 | 说明 |
|------|------|
| credit | 计费单位，1 credit = 1 分钟音频时长 |
| 引擎 | 语音识别引擎（local_whisper / openai_whisper / cohere） |
| 收藏集 | 命名的句子收藏组，可跨任务 |
| 公共库 | 用户公开的任务集合，供其他用户浏览 |
| TaskWorker | 后台任务处理线程，管理队列和流水线 |
| 预扣 | 任务提交时预估扣费，完成后结算差额 |
| 自建 Anki 服务器 | 平台托管的 Anki 同步服务器，通过 sync_client 协议推送 |
| AnkiWeb | Anki 官方云同步服务 (ankiweb.net)，通过官方同步协议推送 |
| 推送配置 | 用户保存的 Anki 推送凭证和参数，支持自建服务器和 AnkiWeb 两种模式 |
